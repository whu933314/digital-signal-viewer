# Digital Signal Viewer（DSV）版本紀錄 CHANGELOG

每個版本新增、改變了什麼，從最新的 1.0.1 一路回到 v3.x。這份檔案給「以後接手的人（或沒有任何記憶的新 session）」看：
要知道某個功能是哪一版加的、當時的行為是怎麼決定的、哪些是刻意改掉的（不算壞掉）、哪些是當時就知道還沒修的，都查這裡。
功能的完整清單（「現在有什麼」）在 `docs/FEATURES.md`；深度檢查怎麼跑也在那裡。這份檔案只記「每一版帶來了什麼」。

> 公開檔案：這份檔案跟著專案推上 GitHub，所以只寫行為與決定，不寫任何個人路徑、帳號、機器名稱、行程編號。
> 位置一律用通稱：「使用者家目錄的 `.signal_viewer_last.json`」「Windows 的 `%LOCALAPPDATA%\SignalViewer`」「專案的 `audit/` 資料夾（只在本機、不上傳）」。

## 維護規則（每次改版都要做）

**使用者的指示（2026-11-01）：「每次改版完都要把新增的功能詳細寫下來」。**

1. **發布流程的最後一步**（打包、推上 GitHub 之後、宣告「已發布」之前）：在這份檔案最上面加一節 `## x.y.z（YYYY-MM-DD）`，
   並同步更新 `docs/FEATURES.md`（新功能加進功能清單、刻意改掉的行為改寫、已知問題同步）。沒寫完這兩份就不算發布完成。
2. **每一節都照下面的格式寫**，缺的子節寫「無」，不要省略：
   ```
   ## x.y.z（YYYY-MM-DD）
   一句話：這版是什麼（例：第四批 MATLAB 工具；Windows 收尾）。發布到哪些平台（Mac App／Windows exe／只有原始碼）。
   ### 新增功能        ——每項一條：在哪裡（分頁／右鍵／快速鍵）、怎麼用、行為是什麼；不是只寫名字。
   ### 行為改變        ——「以前 → 現在」，並寫明是「使用者決定（日期）」還是「修正（修了什麼錯）」。刻意改掉的行為寫在這裡，下一版檢查時才不會被當成壞掉。
   ### 資料安全與相容性 ——設定檔／自動存檔的鍵與版本、舊版開新版的檔會怎樣、備份／佔位／凍結檔的規則、檔案格式。
   ### Windows         ——Windows 專屬的修正、打包、有沒有在實機驗證。
   ### 測試與工具      ——新測試步驟、測試工具的改動、發布前跑了哪幾套（簡短）。
   ### 已知問題        ——這版發布時「已經知道、決定留著」的問題，寫明留到哪一版。
   ```
3. **寫法**：繁體中文、台灣用語（檔案、資料夾、滑鼠、介面、程式、視窗、設定、匯出、快速鍵）；只寫查證過的事（程式、README、測試、git、決定檔），
   不確定就寫「紀錄不明」，不要猜。使用者的決定寫成「使用者決定（YYYY-MM-DD）」，不要抄決定檔裡的私人細節。
4. **來源**：commit 訊息（都是中文、寫得很細）、`README.md`（每個功能一節，常註明「x.y.z 起」）、專案本機的 `VERSION_LOG.md`
   （commit／推送／打包時間與測試結果，不上傳）、本機 `audit/` 裡的決定檔（`decisions_*.md`、`todo_*.md`）。
5. **下一版怎麼用這份檔案檢查**：發布前把「上一版」那一節的新增功能、行為改變逐項對照——每一項都要還在、行為一樣；
   不一樣的只有兩種可能：這版「行為改變」裡有寫（使用者決定或修正），不然就是回歸，一律修。這就是使用者說的
   「不能因為改版，已經有的功能就壞掉不能用或不見」。

**版本號規則**（0.9.1 起）：`x.y.z`，每次小改動只動 z（`python3 tools/bump_version.py patch`）；x／y 只在使用者說「大改版」「中改版」時動。
`signal_viewer.py` 的 `APP_VERSION` 是唯一來源：視窗標題、設定檔 `app_version`、Windows exe 檔案版本、macOS App 的版本字串都用它。

**git 歷史注意**：main 的歷史在 2026-10-24 改寫過一次（整理掉不該上傳的內容），所以 v3.4～0.9.5 第一次推上去時的 commit 編號和現在 main 上的不同；
這份檔案寫的是現在 main 上的編號。
